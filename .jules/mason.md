## 2025-03-01 - Move GridView KeyDown event to Attached Property
**Learning:** In WinUI 3, `ListViewBase` controls (like `GridView`) do not natively fire the `ItemClick` event on an `Enter` key press, even when `IsItemClickEnabled` is true. To implement MVVM-friendly keyboard navigation without code-behind, an attached property can subscribe to the `KeyDown` event, explicitly check for `VirtualKey.Enter`, resolve the focused item via `FocusManager.GetFocusedElement(xamlRoot)`, and execute an `ICommand` using the focused element's `DataContext`.
**Action:** When implementing keyboard navigation for item selection in WinUI 3 `ListViewBase` controls, avoid code-behind event handlers. Instead, extend or create attached properties (like `ListViewBaseExtensions.CommandProperty`) that handle both `ItemClick` and `KeyDown` events to provide a unified MVVM integration point.

## 2026-08-31 - Re-evaluating UI Event Handling in MVVM
**Learning:** The previous entries (2025-03-01 and 2026-05-11) recommended using attached properties to route UI events (like `KeyDown`) to ViewModels, and using View-level event subscriptions to handle UI focus changes triggered by the ViewModel. This approach led to ViewModels importing UI-specific types (e.g., `VirtualKey`) and acting as UI coordinators, which violates MVVM principles by making them platform-dependent and harder to test.
**Action:** For simple, synchronous, input-driven UI state changes (like keyboard navigation or focus management), it is structurally cleaner to handle the raw UI event (e.g., `KeyDown`) directly in the View's code-behind. The code-behind should act as a mediator: it calls pure, UI-agnostic business logic methods on the ViewModel (e.g., `TryLaunchSelected()`), and then directly manipulates the UI state (e.g., setting `e.Handled = true` or calling `Control.Focus()`) based on the result. This keeps ViewModels strictly focused on state and business logic.
